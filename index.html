Spec · open-company/v0

Open Company

一家可以 Fork 的公司，由 Agent 运营。这一站只回答一个问题：一家公司包长什么样。读完可以写出一份通过 Schema 校验的 Companyfile.yaml。

A company you can fork, run by agents. This site answers one question: what a company package looks like. From this page you can write a Companyfile.yaml that validates against the schema.

三条原理Three principles

01

一家公司就是一个仓库。 A company is a repository.

公司的做法写成文件：约定、产品声明、运营与发版的剧本、专员、Skill。一个人加上一条产品，就是最小的一家公司。v0 把这个目录放在 GitHub 仓库或本机文件夹里。

The company's practice is files: agreements, product declarations, operating and release playbooks, agents, and skills. One person and one product are already a company. In v0 that directory lives in a GitHub repository or a local folder.

02

运行时把它跑起来，人在路口拍板。 A runtime runs it; a person decides at the intersections.

运行时执行这份目录。人在路口拍板：导入先给出预览，确认之后才写入；声明里的日程在导入后关着，由人打开。

A runtime executes the directory. A person decides at the intersections: import shows a preview and writes only after confirmation, and declared schedules stay off until a person turns them on.

03

Fork 了就是你的。它带走的是做法，不是实例数据，也不是密钥。 A fork is yours. It carries the practice, not the data or secrets.

导入就是 Fork。之后这家公司是你的，不跟上游同步。包里是做法。密钥的值、实例记录和本机路径留在原地。

Import is the fork. Afterwards the company is yours, with no sync to upstream. The package carries the practice. Secret values, instance records, and machine-local paths stay behind.

目录Directory

公司包是一个目录。导出时不带 .git。产品、专员和 Skill 靠路径发现，Companyfile.yaml 里不再列一遍。

A company package is a directory. An export has no .git directory. Products, agents, and skills are discovered by path. Companyfile.yaml does not list them again.

my-company/
  Companyfile.yaml
  AGENTS.md
  LICENSE
  skills/{id}/SKILL.md
  agents/{id}.md
  projects/{id}/
  products/{id}/
    Productfile.yaml
    AGENTS.md
    goal.md
    code/
    projects/{id}/
      README.md
      tasks/{id}.md
      .opencode/
  • Companyfile.yaml — 公司声明。字段见下一节。The company declaration. Fields are in the next section.
  • AGENTS.md — 公司约定。有才放。Company agreements. Include the file when you have them.
  • LICENSE — 作者自选。运行时不解析，导出也不替你生成。The author's choice. A runtime does not parse it, and export does not invent one.
  • skills/{id}/SKILL.md — 公司级 Skill。一个 id 一个目录。Company skills. One directory per id.
  • agents/{id}.md — 公司级专员。Markdown，元数据放在文首。Company agents. Markdown, with metadata in frontmatter.
  • projects/{id}/ （公司根下）(at the company root) — v0 只预留这个位置。导入时警告并跳过，导出不写出。Reserved in v0. Import warns and skips it. Export does not write it.
  • products/{id}/Productfile.yaml — 一条产品一份声明。id 等于目录名 {id}。One declaration per product. id equals the directory name {id}.
  • products/{id}/AGENTS.md — 产品约定。有才放。Product agreements, when you have them.
  • goal.md — 可选。模板默认不带。Optional. Templates leave it out by default.
  • code/ — 只在 source.path 时出现。源码快照，不含 .git。Present only for source.path. A source snapshot, with no .git.
  • products/{id}/projects/{id}/ — README.md 是项目说明书。tasks/{id}.md 一条任务一个文件，不写进 Productfile.yaml。README.md is the project brief. tasks/{id}.md is one task per file, and tasks are not fields of Productfile.yaml.
  • .opencode/ — 可选。按它自己的约定原样保留。规范不解析它，其中不能有密钥。Optional. Kept as its own convention. The spec does not parse it, and it must not contain secrets.

两份声明Two declarations

Companyfile.yaml 描述这家公司。每个 products/{id}/Productfile.yaml 描述一条产品。两份都是 YAML，spec 都写成 open-company/v0。空列表和关着的开关不写出来。不认识的键，除了 x-*，都会使文件不合法。

Companyfile.yaml describes the company. Each products/{id}/Productfile.yaml describes one product. Both are YAML, and both set spec to open-company/v0. Omit empty lists and switches that are off. Any unknown key other than x-* makes the file invalid.

Companyfile.yaml

公司声明。产品、专员、Skill 都在目录里，不在这个文件里列清单。

The company declaration. Products, agents, and skills live in the directory, not as a list in this file.

字段Field 何时要写When required 规则Rule
spec 必写Always open-company/v0
id 写出时要带。读旧包时可以没有。Include it when writing. Older packages may omit it. UUID。它标出这份包是从哪一家公司写出来的。改 name 不改 id。导入不把它变成导入方自己的 id；再次导入时用它认出同一个包。A UUID. It identifies the company that wrote the package. Renaming does not change it. Import keeps the importer's own id and uses this value to recognize the same package later.
name 必写Always 显示名。去掉首尾空白后 1–200 个字符，可以有空格，可以用任何文字。它不是查找键。Display name. After trimming whitespace, 1–200 characters. Spaces and any language are allowed. It is not a lookup key.
description 可选Optional 一句话。写了就不能是空白。One line. If present, it is non-empty after trimming.
homepage 可选Optional 一个 URL。A URL.

最小的一份合法文件只需要 spec 和 name。新写的包带上 id。

The smallest valid file has spec and name. A newly written package includes id.

Companyfile.yaml 示例文件Example file 
spec: open-company/v0
id: 7c9e6679-7425-40de-944b-e07fc1f90ae7
name: Acme Labs
description: 一句话说明这家公司做什么
homepage: https://acme.example

Productfile.yaml

产品声明，放在 products/{id}/Productfile.yaml。id 与目录名相同。任务在 projects/{id}/tasks/ 里，不在这个文件里。

The product declaration, at products/{id}/Productfile.yaml. id matches that directory name. Tasks live under projects/{id}/tasks/, not in this file.

字段Field 何时要写When required 规则Rule
spec 必写Always open-company/v0
id 必写Always 等于所在目录名。小写 kebab：以字母开头，后面最多 47 个 a-z、0-9 或 -。正则 ^[a-z][a-z0-9-]{0,47}$。Equals the directory name. Lowercase kebab: a letter, then up to 47 of a-z, 0-9, or -. Pattern ^[a-z][a-z0-9-]{0,47}$.
title 必写Always 显示标题。去掉首尾空白后不能为空。Display title. Non-empty after trimming.
lifecycle 必写Always explore、live、maintain、frozen 之一。导入时可以改。One of those four. It may be changed at import.
source 必写，二选一Always, one form 用键名区分，不另设 type。git 与 path 只能出现一个。没有第三种「本机路径」形态。The key name is the form. There is no type field. git and path are mutually exclusive. A machine-local path is not a third form.
source.git git 形态必写Required for git 仓库 URL。导入时 checkout 到 commit。这个提交要已经在该 GitHub 仓库上。Repository URL. Import checks out commit. That commit already exists on the GitHub repository.
source.path path 形态必写Required for path 固定为 ./code，相对这份 Productfile.yaml。快照不含 .git。Exactly ./code, relative to this Productfile. The snapshot has no .git.
source.commit 两种形态都必写Required in both forms 7–64 位十六进制 SHA，大小写都可以。git 形态是要 checkout 的修订。path 形态只说明快照取自哪次提交。A 7–64 character hex SHA, either case. For git, the revision to check out. For path, provenance of the snapshot only.
source.branch 两种形态都必写Required in both forms 非空分支名。path 形态导入后，新仓库从这条分支开始。A non-empty branch name. For path, the new repository starts on this branch.
requires 可选Optional 导入方要自己准备的东西，只写名字。没有就整段省略。What the importer prepares. Names only. Omit the object when there is nothing to name.
requires.secrets 可选Optional 密钥名。写了这个键，至少一项，每一项去掉空白后非空。不写值。Secret names. If the key is present, at least one item, each non-empty after trimming. Values stay out.
requires.logins 可选Optional 要人在自己机器上先登录的平台名。规则与 secrets 相同。运行时不为这些名字做平台适配。Platform names a person logs into on their own machine. Same list rule as secrets. A runtime does not add platform adapters for these names.
groups 可选Optional 列表顺序就是分组顺序。每一项有 id（同上的 kebab）和 title（非空）。没有就省略。List order is the group order. Each item has id (the same kebab pattern) and a non-empty title. Omit the key when there are none.
projects 可选Optional 每一项有 id、title，以及可选的 group（某个分组的 id）。任务不写在这里。Each item has id, title, and an optional group (a group id). Tasks are not listed here.
source.git示例文件Example file
spec: open-company/v0
id: munk-mind
title: Munk Mind
lifecycle: live
source:
  git: https://github.com/owner/munk-mind
  commit: 3f2c1a9
  branch: main
requires:
  secrets: [apple-asc]
  logins: [feishu]
groups:
  - id: acquire
    title: 获客
projects:
  - id: feedback
    title: 用户反馈
    group: acquire
source.path
spec: open-company/v0
id: munk-mind
title: Munk Mind
lifecycle: live
source:
  path: ./code
  commit: 3f2c1a9
  branch: main

products/munk-mind/code/ 只跟 path 这一份走。同一个 source 对象里只写 git 或 path 其中一种。Schema 检查形状。产品 id 与目录名一致，group 指向同文件里的分组，这两条由你按上面的规则对齐。

products/munk-mind/code/ belongs with the path form. One source object carries either git or path. The schema checks shape. You keep the product id equal to the directory name, and point group at a group in the same file.

任何对象都可以带 x- 加厂商名的键，例如 x-example。键名匹配 ^x-[A-Za-z0-9][A-Za-z0-9-]*$。v0 读的时候留着它们，再写文件时不带回去。

Any object may carry a vendor key such as x-example. The name matches ^x-[A-Za-z0-9][A-Za-z0-9-]*$. v0 keeps them when reading and leaves them out when writing the file again.

如何导入How import works

导入的是上面这个目录。v0 的来源是本机目录，或一个 GitHub 仓库 URL（可以带 ref）。没有注册中心。

Import takes that directory. In v0 the source is a local directory, or a GitHub repository URL with an optional ref. There is no registry.

  1. 把目录交给一个实现了这份规范的运行时。根上要有 Companyfile.yaml。产品在 products/{id}/。 Give the directory to a runtime that implements this spec. The root contains Companyfile.yaml. Products are under products/{id}/.
  2. 运行时先给预览：将要加入的产品、项目、任务、专员和 Skill，以及要人补上的项（代码放在哪、密钥叫什么名字）。确认之前不写入。 The runtime previews first: products, projects, tasks, agents, and skills it would add, plus what a person still supplies (where code goes, and the names of secrets). It writes nothing before confirmation.
  3. 人确认之后才写入。包里的 id 仍是写出这份包的那家公司的 uuid。导入方保持自己的 id，并用包里的 id 在下次导入时认出同一个包。 A person confirms, and then it is written. The package id stays the uuid of the company that wrote it. The importer keeps its own id and uses the package id to recognize the same package on a later import.
  4. 导入之后就是导入方自己的公司。不记录上游地址，不提示有新版本，也不把改动送回上游。要公开这份目录，由人自己初始化 git 再推送。 After import the company is the importer's. The import records no upstream URL, offers no update, and sends no changes back. Publishing the directory is a person's own git init and push.
  5. 任务文件里没有「开着」这个字段。导入后日程关着，由人之后打开。导入不开始工作。 Task files have no on/off field. Schedules stay off after import until a person turns them on. Import does not start work.

source.git

从 git 这个 URL checkout 到 commit，再从 branch 接着走。人可以把 URL 换成自己 Fork 的地址。v0 不替人创建那个 Fork。

Check out commit from the git URL, then continue from branch. A person may substitute the URL of their own fork. v0 does not create that fork.

source.path

把 products/{id}/code/ 复制到人指定的位置，建成一个新仓库，起始分支是 source.branch。commit 只记录快照来自哪次提交。

Copy products/{id}/code/ to a place the person chooses and create a new repository whose first branch is source.branch. commit records which commit the snapshot came from.

JSON Schema

文件是 YAML。Schema 校验的是解析之后的对象，草案 2020-12。下面两个地址属于 v0，之后不改内容、不改路径。

The files are YAML. The schema validates the parsed object, draft 2020-12. These two v0 URLs keep their path and their meaning.

/schema/v0/companyfile.json

/schema/v0/productfile.json

它们由 companyfileSchema 与 productfileSchema 的字段约束，用 zod v4 的 z.toJSONSchema 生成。导出的 schema 用一层变换放行 x-*，JSON Schema 表达不了这层变换，所以每个对象用 patternProperties 放行同样的键，其余未知键拒绝。commit 在源 schema 里不区分大小写，生成结果把字符类写成 [0-9a-fA-F]。

They were generated with zod v4 z.toJSONSchema from the field constraints of companyfileSchema and productfileSchema. The exported schemas allow x-* through a transform JSON Schema cannot represent, so each object allows the same keys with patternProperties and rejects every other unknown key. commit is case-insensitive in the source schema; the generated pattern uses [0-9a-fA-F].

长度按去掉首尾空白之后计算。JSON Schema 的 minLength / maxLength 作用在原始字符串上，不会先裁空白。参考实现会先裁。另外，Schema 不检查产品 id 是否等于目录名，也不检查 group 是否指向同文件里的分组。

Length is measured after trimming. JSON Schema minLength / maxLength apply to the raw string and do not trim. The reference check trims first. The schema also does not check that a product id equals its directory name, or that group points at a group in the same file.
